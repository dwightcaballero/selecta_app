SELECTA APP - ZERO-COST AI SCAN & CHAT IMPLEMENTATION PLAN (FOR REVIEW)
=======================================================================

Goal: stop depending on slow / unreliable Gemini vision calls and run the AI
features at $0 (or as close to $0 as possible), while keeping accuracy and
the existing screens and call sites unchanged.

Status: PLAN ONLY. Nothing in this file has been implemented yet.
Note: provider free-tier limits and model names change often. Every number
marked (verify) must be re-checked on the provider's dashboard before Phase 0
sign-off. Limits quoted here came from a general web summary, not from
benchmarks on Selecta invoices.

1. BACKGROUND (WHAT EXISTS TODAY)
=======================================================================
All AI goes through lib/services/gemini_ai_service.dart (singleton
GeminiAiService, SDK google_generative_ai ^0.4.7, deprecated, no thinkingConfig).

Vision flows (image in -> JSON out) - the slow ones:

downscaling, catalog trimming, 45 s timeout, remembered working model, cache of

Existing assets we can reuse:

- Android minSdk 26 (ML Kit needs 21+, OK). App uses Bluetooth printer, SMS,
  barcode scanner -> primarily an Android (and iOS) app.


=======================================================================
2. TARGET ARCHITECTURE
=======================================================================
Stop sending images to a cloud LLM. Read the text on the phone, match
products locally, and only call a free text-only LLM for lines that the local
matcher cannot resolve.

   photo(s)
      |
      v
   [A] ImagePrep (existing prepareImageBytesForAi / slicing)
      |
      v
   [B] OcrService  --- Google ML Kit Text Recognition (on-device, free,
      |                  unlimited, offline). Returns text blocks/lines with
      |                  bounding boxes.
      v
   [C] DocumentLayoutParser  --- groups lines into rows by Y position, finds
      |                         header, invoice no., date, total, and for each
      |                         row: code, description, qty, unit price, amount
      v
   [D] CatalogMatcher  --- alias exact -> item code -> fuzzy name -> price check
      |                    gives matched / ambiguous / unmatched + confidence
      v
   [E] decision: enough confident? ----yes----> result (no network at all)
      |
      no (unresolved lines only)
      v
   [F] TextLlmProvider chain (free tiers, TEXT ONLY, tiny prompt):
         1) Gemini Flash-Lite free     2) Groq free     3) none -> manual
      |
      v
   result -> existing models -> existing UI (disambiguation sheet etc.)

Key properties
- Image bytes never leave the device in the default mode (privacy + no quota).
- Typical scan: ~1-3 s OCR + local matching; LLM only for leftovers.
- Everything degrades gracefully: no network / quota exhausted still returns
  a usable result with unmatched lines for manual pick.
- Public method signatures on GeminiAiService stay the same so the 5 call
  sites do not change in the first rollout.

Scan modes (remote-configurable by superadmin, stored in Configuration):
- ocr_local   : steps A-D only, never calls an LLM
- hybrid      : A-F (DEFAULT after rollout)
- cloud_vision: today's behavior (Gemini image call). Kept as an emergency
                fallback and for web/desktop where ML Kit is unavailable.

4. DESIGN DETAILS
=======================================================================
4.1 OCR (ML Kit)
- Package: google_mlkit_text_recognition (Latin script, bundled model so it
  works offline; adds a few MB to the APK - check size impact).
- Wrap behind an abstract OcrEngine { Future<OcrResult> recognize(bytes) } so
  tests use a fake and web/desktop can return "unsupported".
- OcrResult: pages -> blocks -> lines -> elements, each with text + rect +
  confidence (where provided).
- Run image prep first (already 1600-2000 px, q80). For long screenshots reuse
  ImageSlicingService; de-duplicate overlapping rows at slice boundaries
  (equal normalized text + same qty + adjacent y) - replaces the prompt rule
  "prevent duplicates from overlaps".
- Run OCR on images concurrently (limit 2-3 at a time) in an isolate-safe way
  (the plugin already runs natively off the UI thread).

4.2 Layout parsing
- Cluster lines into rows: same row if vertical centers within ~0.6 x median
  line height. Sort each row left to right.
- Detect header row via keywords (QTY, QUANTITY, DESCRIPTION, ITEM, PRICE,
  AMOUNT, UNIT, CODE) to learn column x-ranges; fall back to regex when no
  header (screenshots of ordering apps).
- Extract per row: item code (digits / alphanumeric token matching catalog
  codes), description text, qty, unit price, line amount, UOM (CS/BOX/PC/PCS).
- Quantity rules ported from the current prompt:
  * prefer delivered/invoiced qty over ordered qty when both columns exist
  * never treat unit price, line amount or item code as qty
  * sanity check: qty x unit price ~= line amount (+/- rounding); use it to
    pick the right number and to flag suspicious rows
  * digit confusions (1/7, 3/8, 5/6, 0/8, O/0, l/1) corrected inside numeric
    fields only
- Header fields: invoice number (regex near INVOICE / SI / DR / PO labels),
  date (several PH formats -> yyyy-MM-dd), total (largest amount near TOTAL /
  AMOUNT DUE / GRAND TOTAL, cross-check = sum of lines when available).
- Each parsed row carries a confidence; rows that fail sanity checks are
  marked needsReview.
- Parser is per-document-type: PurchaseOrderParser, StoreReceiptParser,
  SupplierStockParser, with shared row clustering utilities.

4.3 Catalog matching (CatalogMatcher)
Order of resolution for each row:
 1. Learned alias exact normalized match (SupplierMappingService, incl. prefix
    match for truncated text with "..."). Multi-variant alias -> ambiguous.
 2. Item code exact match against InventoryItem.itemCode.
 3. Fuzzy name match: normalize (lowercase, strip punctuation, expand known
    abbreviations such as CORN -> CORNETTO, MAG -> MAGNUM, WH -> WHITE; build
    this dictionary from existing mappings), token-set similarity +
    Jaro-Winkler / trigram, pre-filtered by an inverted token index so it is
    fast on a few thousand items.
 4. Price verification: unit price on the document vs catalog buyingPrice
    (PO) or sellingPrice (store receipt) within a tolerance; use it to
    separate sizes (pint vs tub) and to break ties.
 5. Score bands: >= 0.90 matched; 0.60-0.90 ambiguous (top 3-5 candidates
    for the existing disambiguation sheet); < 0.60 unmatched.
- Cache normalized catalog + token index per scan session (rebuild when
  ProductCatalogCache changes).
- Source filtering stays: OOS flow only matches InventoryProductSource.selecta;
  PO flow can pre-filter by supplier when known, with full-catalog fallback.
- Output mapped to existing ExtractedPoItem / AmbiguousPoItem / unmatched.

4.4 Text LLM step (hybrid only)
- Triggered only when unresolved rows exist (ambiguous or unmatched), or when
  header fields (invoice no./date/total) could not be parsed.
- Prompt contains ONLY: the unresolved raw lines + each line's top-5 candidate
  products (id, name, price) + header text snippets. No full catalog, no
  images -> a few hundred tokens, answers in ~1-3 s.
- JSON-mode response: [{row, product_id|null, qty, confidence}] and header
  fields. Validate every returned product_id exists in the catalog; ignore
  anything invalid (hallucination guard).
- Result merges back; LLM answers never override a confident local match.
- Provider chain with circuit breaker (see 4.6).

4.5 Other flows
- compareOfficialInvoiceWithPoItems: OCR + parse the invoice, then match its
  rows to the original PO items (by product id mapping/name/code) ->
  confirmed / adjusted qty / missing. LLM only for unresolved rows.
- extractSupplierStockStatusFromImages: parse rows, detect OOS markers (OOS,
  OUT OF STOCK, N/A, NONE, 0, strike-through not detectable -> rely on text),
  available qty column when present. Match only Selecta products.
- Chat (Sedy): move to TextLlmProvider chain (Gemini Flash-Lite free ->
  Groq). Keep conversation history in-app and send last N turns, since REST
  calls are stateless.

4.6 Providers, quotas and resilience
- Abstract interface:
    abstract class TextLlmProvider {
      String get id;
      Future<String> generateJson(prompt, {schemaHint, timeout});
      Future<String> chat(messages, {systemPrompt, timeout});
    }
- Implementations call REST with the existing http/dio package (no SDK):
    GeminiTextProvider  -> generativelanguage.googleapis.com generateContent
                           (model: a Flash-Lite model, thinking disabled via
                           thinkingConfig/budget 0 if supported (verify))
    GroqTextProvider    -> api.groq.com/openai/v1/chat/completions
                           (OpenAI-compatible; JSON mode; a Llama/GPT-OSS
                           text model (verify current free model list))
- Model names live in remote config (Configuration/Firestore), NOT hardcoded,
  so a retired model is fixed without an app release. Keep a safe default list
  in code.
- Quota guard: count requests per provider per day (+ per minute in memory);
  stop at ~80% of the known free cap and skip to the next provider.
- Error handling: 429 / 503 -> open a circuit for Retry-After (or 60 s),
  move to next provider; 401/403 -> mark key invalid and show the existing
  "key needed" message; timeout 15 s for text calls, max 1 retry.
- Final fallback: return the local result (matched + unmatched) and let the
  user resolve manually - the flow never hard-fails because AI is down.
- Remove google_generative_ai from pubspec once Gemini goes through REST
  (last step, behind the mode flag).

4.7 Configuration / keys
- Configuration model: add groqApiKey, aiScanMode, aiProviderOrder,
  textModelGemini, textModelGroq, ocrMatchThresholds (optional).
- Superadmin page: add Groq key field, scan mode selector, provider order,
  per-provider daily counters, "test connection" buttons.
- Keys are stored in Firestore config and fetched by the client (as today).
  Because free-tier keys are extractable from a client, the worst case is
  quota exhaustion, which the local-first design tolerates. Review
  firestore.rules so only authenticated app users can read config.
- If stronger protection is wanted later, a Cloud Function proxy is possible
  but needs the Blaze plan (not $0) - intentionally out of scope.

8. RISKS & MITIGATIONS
=======================================================================
- OCR misreads on blurry / thermal-faded paper
  -> sanity checks, needsReview flags, cloud_vision fallback mode, UX hint to
     retake photo when OCR confidence is low
- Parser breaks on a new supplier layout
  -> regex fallback + LLM step for unresolved rows + Phase 6 sample review;
     per-supplier profiles in Phase 8
- Wrong confident match (silent error) is the worst failure
  -> conservative thresholds, price verification, user always reviews the
     summary screen (existing flow), track wrong-confident rate in Phase 6
- Free tier changes or is removed
  -> provider chain, remote model/provider config, local-first design means
     most scans need no API
- Free-tier data may be used by the provider to improve products
  -> accepted by owner: images never sent, only short text of unresolved
     item rows; documents are cropped before scanning
- Shared key extractable from the client
  -> free tier only; quota guard; rotate key from superadmin if abused
- ML Kit not available on web/desktop
  -> force cloud_vision there; keep Gemini vision code
- APK size increase from bundled ML Kit model
  -> measure in Phase 2; acceptable only if increase is a few MB
- Larger refactor touches all AI flows
  -> mode flag, unchanged signatures, staged rollout, one-tap rollback
