HAPI STORE SELF-ORDERING - IMPLEMENTATION PLAN (FOR REVIEW)
===========================================================

GOAL
----
Let stores order by themselves. A new user role "Hapi Store" can place orders
with their ONE dealer, track order status, and see their own performance, all
in a separate store-only dashboard.

DECISIONS (confirmed)
---------------------
1. Each Firebase database belongs to exactly ONE dealer, so every store in
   it belongs to that dealer. There is no dealer field, dealer lookup or
   dealer validation anywhere in the store flow. (In future each dealer gets
   their own Firebase database/project; this design needs no change for it.)
2. Stores can ONLY order. No payments, credit or credit limits in the app.
   Payment is settled on delivery by the salesman (existing delivery flow).
3. One price list only: Selecta product sellingPrice.
4. Price is RECOMPUTED at dealer approval using current sellingPrice. The
   price the store sees at submit time is an estimate only.
5. Stores see availability only ("Available" / "Out of stock"), never stock
   quantities.
6. Stores do NOT choose a delivery date. The dealer assigns it on approval.
7. Cut-off time and minimum order value are optional settings in the
   existing configuration doc.
8. NO auto-approve. The dealer reviews every order from every store.
9. Store login: unique store USERNAME + password. Accounts are not
   self-registered; the dealer or Admin creates them (salesmen cannot).
10. Every store starts with the default password and MUST change it on first
    login. Stores may change it again anytime. Forgotten passwords are
    recovered by the dealer/Admin "Reset Password" action (passwords are
    never viewable).
11. Lockout: 5 failed attempts -> 15 minute lock.

DESIGN PRINCIPLE
----------------
A store order is a "pre-sell" order that the store books itself. It must feed
the EXISTING Delivery / inventory / salesman flow instead of creating a
parallel system. The store sees a simplified status view of the same order.

  Store submits order  ->  Dealer approves  ->  Delivery doc (pre-sell)
  created  ->  salesman delivers and collects payment  ->  store sees
  "Delivered".

DATA MODEL
----------
A. Role (lib/data/constants.dart)
   + BusinessRole.hapiStore = "Hapi Store"

B. Users (lib/models/users.dart)  [users/{uid}]
   + storeId:   String   (id of the Hapistore doc; '' for staff)
   + storeName: String   (denormalised for display/queries)
   + getter isStore => role == BusinessRole.hapiStore
   Update fromJson / fromSnapshot / copyWith / toJson.
   + mustChangePassword: bool (stores only)
   users/{uid} for a store is created by createStoreAccount (see 1.3).

C. Hapistore (lib/models/hapistore.dart)
   + storeUserUid: String? (linked app account, if any)

D. New collection store_orders/{orderId}
   {
     orderNo, storeId, storeName,
     status: 'Submitted' | 'Approved' | 'Rejected' | 'Cancelled'
             | 'Out for Delivery' | 'Delivered',
     items: [ { productId, name, uom ('piece'|'case'), qty, unitPrice,
                lineTotal, qtyApproved } ],
     totalAmount, approvedAmount,
     deliveryDate (assigned by dealer on approval; null until then),
     remarks, rejectReason,
     source: 'store',
     deliveryId: String?            (set when Delivery is generated)
     statusHistory: [ { status, at, byUid, byName } ],
     createdBy (uid), createdAt, updatedAt
   }
   unitPrice is the sellingPrice at submit time (estimate). On approval the
   service re-reads current sellingPrice, overwrites unitPrice/lineTotal and
   sets approvedAmount. The store sees the final amount after approval.

E. Notifications
   Reuse firebase_messaging / existing notifications_page:
   - Dealer + assigned salesman: new store order.
   - Store: approved / rejected / out for delivery / delivered.

PHASES
------
PHASE 1 - Foundation (roles, accounts, routing, security)
  1.1 Add BusinessRole.hapiStore and Users.storeId/storeName/isStore.
  1.2 Add Hapistore.storeUserUid, orderingEnabled (default true) and
      username display on hapistore_page.dart. No dealer fields and no
      backfill needed.
  1.3 Store accounts and login (username + password)
      Account creation (dealer/Admin, on hapistore_page.dart):
      - "Create Store Login" asks for a USERNAME and creates the account.
        Username rules: lowercase letters/digits/._-, 4-20 chars, GLOBALLY
        unique (enforced by a `store_usernames/{username}` doc created in a
        transaction, value = storeId). One login per Hapistore. This removes
        the duplicate store-name problem: the username, not the store name,
        identifies the account.
      - Backend creates a real Firebase Auth user (Admin SDK, in a callable
        Cloud Function `createStoreAccount`, so the dealer is not signed
        out) with synthetic email <username>@store.selecta.invalid, the
        DEFAULT password, and custom claims { role: 'Hapi Store', storeId }.
        It also writes users/{uid} (role, storeId, storeName,
        mustChangePassword: true).
      - Default password lives ONLY in a server-side secret (Functions
        secret), never in the Flutter app, rules, repo or this plan.
      - Any existing Hapistore can be given a login; no other prerequisite.

      Login screen (new, from login_page.dart: "Login as Hapi Store"):
      fields Username, Password only.
      - Callable `storeLogin(username, password)`:
          1. Resolve username -> storeId via store_usernames; confirm the
             store has orderingEnabled == true.
          2. Check lockout: 5 failed attempts for that username -> locked
             for 15 minutes (counter doc store_login_attempts/{username};
             reset on success). Also throttle per IP/device.
          3. Verify the password server-side (Identity Toolkit
             signInWithPassword REST call), then return a custom token
             (uid = store auth uid, same claims). Client calls
             signInWithCustomToken.
      - One generic error for every failure ("Invalid username or password") so usernames cannot be enumerated. Failures are logged.
      - First login with mustChangePassword == true FORCES the Change
        Password screen before the dashboard is shown; the store cannot
        reach any other screen until the new password is set. The same
        applies after a dealer/Admin reset.
      - Hide "Hapi Store" from register_page.dart role choices and from
        changeusernamerole_page.dart so no one can switch into it. Hide
        delete-account for the store role.

      Password change and recovery:
      - Store can change its own password after login (store_account_page):
        callable `storeChangePassword(oldPassword, newPassword)` -> Admin
        SDK updatePassword; clears mustChangePassword. Minimum 8 chars.
      - Dealers/Admin help stores that forgot their password. DECIDED
        model (industry standard): passwords are never stored or viewable by
        anyone. The dealer/Admin gets a "Reset Password" action on the
        store's login: callable `resetStorePassword(storeId)` (Dealer or Admin only;
        salesmen cannot)
        sets the password back to the default (or a generated temporary
        one), sets mustChangePassword = true, and shows it to the dealer
        once to relay to the store owner. Audit-log every reset (who, when).
      - Dealers therefore always "know" the password in the only case that
        matters: right after a reset or before the store's first change.
      - Admin/dealer can disable a store's ordering access
        (Hapistore flag `orderingEnabled`, default true).
  1.4 Role routing: in widget_tree.dart / auth_controller.dart add an
      isStore branch to open StoreShell. Stores never see the staff sidebar
      or staff pages. Update KVariables with getIsStore().
  1.5 firestore.rules:
      - helper isStoreUser(), myStoreId() read from custom-token claims
        (request.auth.token.role / storeId), so no extra
        document reads per request.
      - users/{uid}: user cannot change own role or storeId.
      - store_orders: store may read/create only where storeId == myStoreId()
        and status == 'Submitted' and createdBy == uid; may update only to
        'Cancelled' while status == 'Submitted'. Dealer/Admin full access.
        Salesman read access.
      - selecta products catalog: read-only for stores.
      - Stores may read only their own Hapistore doc (and no write).
      - Deny stores on everything else (deliveries, expenses, payslips,
        inventory, other stores, users).
      - Normalise role strings ('Dealer' vs 'dealer') while editing.

PHASE 2 - Store ordering MVP
  2.1 Model + service + controller:
      lib/models/store_order.dart
      lib/services/store_order_service.dart
      lib/controllers/store_order_controller.dart
  2.2 Store pages (lib/views/pages/store/):
      - store_shell.dart: bottom navigation (Home / Order / Orders / Account)
      - store_catalog_page.dart: product list using existing custom product
        sorting, search, sub-category order, in-stock only (dealer stock),
        piece/case selection, sellingPrice shown. Availability badge only
        ("Available" / "Out of stock", from dealer stockQuantity > 0); no
        quantities exposed. Out-of-stock items cannot be added.
        NOTE: Firestore rules cannot hide a field, so stock must not be
        readable by stores directly. Serve the catalog through a callable
        Cloud Function / small `store_catalog/{productId}` summary docs that
        contains only productId, name, uom, sellingPrice, available, sort
        info (maintained by the function or on stock change).
      - store_cart_page.dart: review, change qty, remarks, submit. No
        delivery date field. Shows "Estimated total - final price is
        confirmed by your dealer". Validate non-empty, qty > 0, and the
        optional minimum order value / cut-off time from configuration
        (skipped when not configured). Orders after cut-off are still
        accepted but labelled for next processing day.
      - store_orders_page.dart: list with status chips, filter by status.
      - store_order_detail_page.dart: items, totals, status timeline from
        statusHistory, "Cancel" button only while Submitted, "Reorder".
  2.3 Order number: running number or date + counter generated
      in a transaction.
  2.4 Notify dealer on submit.

PHASE 3 - Dealer handling and fulfilment link
  3.1 Dealer/Admin "Store Orders" inbox (new sidebar entry, badge count of
      Submitted orders).
  3.2 Review screen: edit approved qty per line (stock shortages), pick the
      delivery date (required to approve), approve or reject with reason.
      Every order requires manual dealer review; there is no auto-approve
      and no setting for it.
  3.3 On approve, re-read current sellingPrice for each line and recompute
      unitPrice / lineTotal / approvedAmount, then create a pre-sell
      Delivery doc (lib/models/delivery.dart) for the store: items ->
      OrderItem, orderType 'pre-sell', deliveryDate = dealer-assigned date,
      current prices, then run the existing inventory reservation path. Save deliveryId on the order.
      Do this in a Firestore transaction (or Cloud Function) so the order
      and Delivery cannot drift.
  3.4 Status sync: when the Delivery moves forward (delivered, van load
      dispatched), update the store_order status and statusHistory and
      notify the store. Payment and credit data on the Delivery are NEVER
      exposed to the store.
  3.5 Salesmen can see approved store orders in their delivery list like any
      other pre-sell order; the PJP visit confirms and collects payment.

PHASE 4 - Store dashboard and performance (read only)
  4.1 store_home_page.dart: open orders, next delivery, last order, quick
      "Reorder last order", announcements/promos if any.
  4.2 store_performance_page.dart (fl_chart), period filter
      (week / month / quarter):
      - Total purchases and order count
      - Average order value
      - Order frequency (days between orders)
      - Top SKUs and category mix
      - Growth vs previous period
      - Fill rate (approved qty / ordered qty)
      - On-time delivery rate (delivered on/before the dealer-assigned
        date)
      - Returns / bad-order rate (from existing returns and badorder data)
      Data source: the store's own store_orders + its deliveries, aggregated
      client side first; move to a Cloud Function / summary doc only if
      volume requires it.
  4.3 store_account_page.dart: store profile (name, dealer, address,
      contact), Change Password, logout.

PHASE 5 - Hardening and rollout
  5.1 Tests: model serialisation, order state transitions, rule tests with
      the Firestore emulator (store cannot read other stores' orders, cannot
      set status beyond Cancelled, cannot edit role).
  5.2 Widget tests for cart totals and role routing.
  5.3 Pilot with a few stores from the dealer, then wider rollout.
  5.4 Cloud Function tests: createStoreAccount (duplicate username),
      storeLogin (unknown username, wrong password,
      5-fail lockout and 15 min expiry, disabled store), storeChangePassword,
      resetStorePassword (only Dealer or Admin), catalog function never
      returns stock numbers.
  5.5 Update README and firestore index definitions
      (store_orders by storeId+createdAt, status+createdAt).

OUT OF SCOPE (v1)
-----------------
- Payments, credit limits, statements of account.
- Price tiers or per-store pricing.
- Multiple dealers per store.
- Recurring / scheduled orders and AI suggested orders (possible later).
- Auto-approval (explicitly not wanted).
- Store-chosen delivery dates.

OPEN ITEMS
----------
None. All design questions are resolved. Minimum order value and cut-off
time default to blank (off) until a dealer configures them.

RISKS
-----
- Security rules are the main risk: a wrongly open rule would expose other
  stores' data. Phase 5.1 emulator rule tests are mandatory before release.
- DEFAULT PASSWORD: all stores start with the same default password, so a
  leaked default plus a guessed username allows login to any store that has
  not changed it. Mitigations: server-side secret only, forced change on
  first login, 5-attempt lockout, generic errors, per-store disable switch,
  audit-logged resets, and rules limiting a store to ordering + its own data
  (no payments/credit/other stores, no stock numbers, cancel only while
  Submitted, every order needs dealer approval). Do not reuse the default
  password for any staff account.
- Username enumeration / brute force: handled by the generic error and
  lockout, but lockout can be abused to lock a store out for 15 minutes;
  accepted, dealer can reset.
