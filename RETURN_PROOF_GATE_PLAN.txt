RETURN PROOF GATE - IMPLEMENTATION PLAN
=======================================

GOAL
----
On the End of Day page, if the day has returned deliveries, or delivered
deliveries with returned items, the salesman must submit proof of return for
EACH affected store, and the warehouse/dealer must CONFIRM receipt, before the
salesman can view or edit the cash breakdown.

DECISIONS (confirmed)
---------------------
1. Warehouse/dealer confirmation is REQUIRED (photo alone is not enough).
2. The gate applies only to transactions created after the release of this
   update. Old/backlog days are never blocked.

EXISTING BUILDING BLOCKS
------------------------
- models/delivery.dart: isReturnIncoming, hasReturnedItems, returnedQuantity,
  isReturnApprovedByDealer, isReturnFinalized (+By/+Date), isRescheduled.
- views/pages/dashboard/return_page.dart + controllers/return_controller.dart:
  existing return handling by salesman.
- models/proof_of_visit.dart + services/proof_of_visit_service.dart: photo
  capture/upload pattern to reuse.
- views/pages/sidebar/endofday_page.dart: validateBeforeBreakdown() and the
  View/Record Cash Breakdown button.
- controllers/endofday_controller.dart: validateBeforeBreakdown() (currently
  only blocks on pendingstatus > 0).
- services/inventory_service.dart: restocks returns on dealer approval.
- firestore.rules: role enforcement.

PHASE 1 - DATA MODEL
--------------------
1.1 Add to Delivery (model, fromJson, toJson, copyWith, DeliveryModelString,
    empty()). Missing fields must default safely (backward compatible):
    - returnProofStatus: String  ('none' | 'submitted' | 'confirmed' |
                                  'rejected' | 'overridden'), default 'none'
    - returnProofUrl: String
    - returnProofNotes: String
    - returnProofSubmittedBy: String
    - returnProofSubmittedDate: Timestamp?
    - returnProofConfirmedBy: String
    - returnProofConfirmedDate: Timestamp?
    - returnProofRejectReason: String
    - returnProofRequired: bool  (default false) -- stamped at creation, see 1.3
1.2 Per-store proof: because proof is per store per day, prefer a separate
    collection "return_proofs" (one doc per store per date) holding:
    id, storeName, proofDate (day key), deliveryIds[], items snapshot
    (deliveryId, productId, name, returnedQty), imageUrl (single), notes, status,
    submittedBy/Date, confirmedBy/Date, receivedQty per item (for variance),
    rejectReason, versions/history.
    Deliveries only keep a lightweight returnProofId + returnProofStatus
    mirror so End of Day can query cheaply.
    (DECIDED: per-store doc. Exactly one image per store per day.)
1.3 Release cutoff (grandfathering):
    - Add a config constant/doc (e.g. app_config/return_proof.enabledFrom
      Timestamp) set to the release date/time.
    - A delivery is "subject to the gate" only if its createdAt (or delivery
      date) >= enabledFrom. Evaluate in ONE helper so rules/UI/controller
      agree. Optionally stamp returnProofRequired=true on new deliveries.
    - Backlog days before enabledFrom: gate never applies.

PHASE 2 - BUSINESS LOGIC (endofday_controller / new service)
------------------------------------------------------------
2.1 New service services/return_proof_service.dart:
    - getReturnsRequiringProof(date): query the day's deliveries where
      (status Returned OR isReturnIncoming OR hasReturnedItems OR
      returnAmount > 0), excluding isRescheduled, and subject to the cutoff.
      Group by store.
    - submitProof(store, date, images, notes): upload (camera only), write
      return_proofs doc, status='submitted', stamp user + server timestamp.
    - confirmProof / rejectProof (dealer/warehouse only): record receivedQty
      per item, flag variance vs returnedQty, reason on reject.
    - getProofStatusByStore(date).
2.2 Extend EndOfDayDTO / endofday data load with:
    - returnStores: list of {store, deliveries, status}
    - hasUnconfirmedReturnProof (bool)
2.3 Extend EndofdayController.validateBeforeBreakdown():
    - after the pending check, throw
      "Proof of return not yet confirmed by warehouse for: Store A, Store B"
      when any gated store is not 'confirmed'.
    - Skip entirely when no gated returns exist or day predates cutoff.
    - Gate applies to the salesman role ONLY. Dealer is never gated and can
      always view/edit the breakdown.
2.4 Re-validate when returns change after proof: compare the stored items
    snapshot with the current returned quantities; if different, reset status
    to 'none'/'submitted' (needs re-proof/re-confirm).

PHASE 3 - SALESMAN UI (endofday_page.dart)
------------------------------------------
3.1 New "Returns Proof" card listing each store with returns:
    store name, returned deliveries/items/qty, status chip
    (Required / Submitted - awaiting warehouse / Confirmed / Rejected + reason).
3.2 "Submit Proof of Return" per store -> bottom sheet/page:
    - shows items and quantities being returned
    - camera-only photo capture (no gallery), exactly 1 photo (required), optional note
    - upload via the same flow as proof of visit; path
      proof_of_return/{yyyyMMdd}/{store}/...
3.3 Button gating: when gated and not all confirmed, replace/disable
    "View/Record Cash Breakdown" with a locked state and message
    ("Waiting for warehouse confirmation of returns").
3.4 Also guard on entry of BreakdownPage (breakdown_page.dart) so deep links,
    back-dated navigation, or the unverified-dates sheet cannot bypass it.
3.5 Refresh status after submit; pull-to-refresh to see confirmation.

PHASE 4 - WAREHOUSE / DEALER UI
-------------------------------
4.1 "Return Receiving" queue (dealer role): list submitted proofs by
    date/store/salesman.
4.2 Detail view: submitted photo, item list, enter received quantity per
    item, Confirm or Reject (reason required).
4.2a Override action: dealer can "Override gate" for a store with a required
    reason (status='overridden', audit fields stored).
4.3 Variance handling: received != returned -> require a note; flag on reports.
4.4 On confirm: set status='confirmed', mirror onto deliveries, and integrate
    with the existing inventory restock/approval path
    (inventory_service.dart, isReturnApprovedByDealer / isReturnFinalized) so
    a confirmation does not double-restock.
4.5 Navigation entry: dashboard sidebar/quick access + badge count of pending
    confirmations.

PHASE 5 - SECURITY (firestore.rules / storage rules)
----------------------------------------------------
5.1 Only salesman creates/updates a proof while status in (none, rejected);
    cannot set confirmed.
5.2 Only dealer role can set confirmed/rejected/overridden, confirmedBy,
    override fields, and receivedQty.
5.3 Submitted proofs immutable except via re-submission (new version, history
    retained).
5.4 Storage rules for proof_of_return/ path (authenticated write, role read).
5.5 Server-side timestamps for submit/confirm dates.

PHASE 6 - REPORTING / AUDIT
---------------------------
- Show return proof status on verified breakdown and End of Day summary.
- Report of returns with proof/confirmation status and variances.
- Keep history of rejected/resubmitted proofs.

PHASE 7 - TESTING
-----------------
Unit (test/):
- Gate helper: no returns -> not gated; full return -> gated; delivered with
  returnedQuantity > 0 -> gated; rescheduled excluded; pre-cutoff excluded;
  mixed stores (one confirmed, one not) -> blocked and names unconfirmed ones.
- validateBeforeBreakdown throws for submitted/none/rejected, passes for
  confirmed/overridden; dealer role is never gated; exactly one photo enforced.
- Return quantity change after proof invalidates proof.
- Delivery model: missing proof fields default safely; round trip toJson.
Manual:
- Salesman flow end to end; warehouse confirm/reject; breakdown unlock.
- Old backlog day with returns remains accessible.
- Offline/failed upload keeps gate closed.
- Firestore rule tests: salesman cannot self-confirm.

ROLLOUT
-------
1. Ship model + rules + warehouse UI first with enabledFrom unset (gate off).
2. Verify warehouse staff can confirm.
3. Set enabledFrom to go-live timestamp; gate applies to new transactions only.
4. Provide a dealer override (with required reason, logged) as an emergency
   escape hatch if the dealer cannot confirm in time (APPROVED).

DECISIONS LOG
-------------
- Proof granularity: per-store doc (return_proofs), one per store per day.
- Gate applies to salesman role only; dealer is never gated.
- Dealer emergency override: ALLOWED. Dealer can unlock a store's gate with a
  required reason; stored as overrideBy/overrideDate/overrideReason on the
  return_proofs doc and shown in reports/audit. Counts as satisfied for the
  breakdown gate (status 'overridden').
- "Warehouse" role = dealer account for now. Keep the role check in one helper
  so a separate warehouse role can be added later without UI/rule rewrites.
- Photos: exactly 1 per store per day (required). Re-submission after
  rejection replaces it; the old one is kept in history.
